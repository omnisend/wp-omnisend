## Summary

- Scope: Replaces the API-key connection screen with an OAuth Dynamic Client Registration flow (register -> authorize -> callback on the admin page -> token exchange -> `/brands/current` read/write), moves every SDK call from `/v3`/`/v5` to `/api` with `Omnisend-Version: 2026-03-15`, centralises request headers (`ApiRequest`) and response parsing (`ApiResponse`), tightens SDK model validation to the new API limits, and bumps the plugin to 1.9.0.
- Risk: **High**. It touches the credential lifecycle and every outbound API call of a plugin other Omnisend plugins depend on, changes the public SDK validation contract (`Omnisend\SDK\V1`), and stores OAuth client secrets/refresh tokens in `wp_options`. The change is large (~40 files, ~2.8k lines of tests) and was already split from several follow-up PRs (#195–#218).
- Positives:
  - Clean separation of concerns: `ApiRequest` (headers/auth mode), `ApiResponse` (status/JSON/RFC 9457 parsing, distinct `WP_Error` codes), `OAuthClient` (DCR/token lifecycle), `Connection` (admin flow). Legacy `/v3` account write is isolated with a clear comment on why it must stay.
  - OAuth basics done right: `hash_equals` on state, one-shot state transient, nonce on flow start, `manage_options` checks on both the flow and the AJAX status endpoint, `wp_safe_redirect` with an explicit allowed-host filter, `PHP_QUERY_RFC3986` encoding, 60 s expiry skew and refresh-token retention when the server does not rotate it.
  - OAuth-connected stores never fall back to the API key; connection state requires both the flag and usable credentials (`Options::is_connected`).
  - Admin-facing error mapping (`get_connection_error_message`) is actionable and names the missing permission scope.
  - Extensive unit coverage: OAuth flow (27 cases), `ApiResponse`, auth-mode switching, client endpoints (~840 lines), SDK validation, Woo hand-over; old REST connect route removal is asserted.
  - Changelog and readme updated; removed filter (`omnisend_signup_wp_link`) is documented.
- Concerns: see the inline findings below. One blocker (unauthenticated callback disconnects an OAuth store), two majors (public SDK validation contract tightened without notice; connected-view/status use the wrong predicate), and a handful of minors/nits.

## Inline findings

### 1. [blocker] Any `?page=omnisend&error=...` (or bad `code`/`state`) request wipes a working OAuth connection

**[file: omnisend/includes/Internal/class-connection.php | lines 306–315, 320–324]**

`complete_oauth_connection()` calls `Options::clear_oauth_tokens()` whenever `try_complete_oauth_connection()` returns a message. That branch is reached for `$_GET['error']` and for a state mismatch **before** any proof that the request belongs to a flow this site started (no nonce, transient state not yet verified for `error`, and `is_oauth_callback()` only needs `page=omnisend&error=x`).

**Why**: An administrator of an OAuth-connected store who follows a crafted link `wp-admin/admin.php?page=omnisend&error=x` (CSRF via image/link, or simply a stale callback tab) loses the access + refresh token and `auth_mode`. Because `clear_oauth_tokens()` also deletes `OPTION_AUTH_MODE` while keeping `OPTION_API_KEY`, a store that was earlier connected with an API key silently falls back to API-key mode — possibly for a *different* brand than the one now stored in `brand_id`. `show_connected_store_view()` still reports connected (see finding 3), so the admin has no visible reconnect path; the SDK just starts returning `omnisend_oauth_no_token` / API-key errors.

The comment on line 310 ("Only the tokens this flow obtained are dropped") is not what the code does: `complete_authorization()` overwrites the existing tokens on success, and on failure the previous tokens are removed too.

**Suggestion**:
```php
// Only drop tokens that this callback actually obtained.
$had_tokens_before = Options::get_oauth_access_token() !== '';
$error_message     = self::try_complete_oauth_connection();

if ( $error_message !== '' && ! $had_tokens_before ) {
	Options::clear_oauth_tokens();
}
```
plus, in `try_complete_oauth_connection()`, verify the pending state transient exists before treating `error=` as a genuine denial (or ignore `error` when there is no pending attempt). Add a test: "callback with error/mismatched state on an already OAuth-connected store keeps the existing tokens".

**Follow-up (author question): can we gate on the option set by `Options::set_store_connected()` instead?**

Only partially. `is_store_connected()` stops the CSRF wipe for an OAuth-connected store, but it is `true` for API-key-connected stores as well, and the failure branch is also reached *after* `complete_authorization()` has already stored new tokens and set `auth_mode = oauth` (platform mismatch, brand read/write error). With a `store_connected` gate those cases are never cleaned up:

- API-key store tries OAuth, brand check fails -> stays in OAuth mode with a token for the wrong brand; the previously working API-key connection is now broken.
- OAuth store re-runs the flow, brand check fails -> the good tokens were already overwritten before the gate is evaluated; skipping the clear keeps the wrong-brand tokens, not the old ones.

Snapshot/restore covers all three cases and keeps the intent of the existing comment:

```php
$previous      = Options::get_oauth_snapshot(); // access, refresh, expires_at, auth_mode
$error_message = self::try_complete_oauth_connection();

if ( $error_message !== '' ) {
	$previous['access_token'] === ''
		? Options::clear_oauth_tokens()
		: Options::restore_oauth_snapshot( $previous );
}
```

Combined with ignoring `error=` / mismatched `state` when no pending state transient exists, a stray or crafted callback becomes a no-op and a genuinely failed re-authorization leaves the store exactly as it was.

### 2. [major] Public SDK validation contract tightened without a compatibility note

**[file: omnisend/includes/SDK/V1/class-batch.php | line 22, 234–239]**
**[file: omnisend/includes/SDK/V1/class-product.php | lines 594–605, 671–681]**
**[file: omnisend/includes/SDK/V1/class-productvariant.php | lines 315–335]**
**[file: omnisend/includes/SDK/V1/class-contact.php | lines 129–185]**

- `Batch::MAX_ITEMS` drops from 1000 to 100.
- `Product::validate()` now requires ≥1 variant, a 3-char currency, identifier-safe `id`/`category_ids`, and RFC-3339 `created_at`/`updated_at`.
- `ProductVariant::validate()` adds `is_valid_price` (max 2 decimals) and identifier rules.
- `Contact::to_array()` moves `tags` handling, drops `contactID`, renames `statusDate` -> `statusChangedAt`, adds `sendWelcomeMessage` per identifier.
- `ContactFactory` reads `id` instead of `contactID`.

**Why**: `Omnisend\SDK\V1` is consumed by the other Omnisend WordPress plugins (forms, Woo, etc.). Objects that validated yesterday will now be rejected client-side (e.g. Woo products with 3+ decimal prices, batches of 101–1000 items, products with no variants). The plugin `readme.txt` changelog only mentions OAuth; nothing tells SDK consumers what changed. The namespace stays `V1`, so consumers cannot detect the new behaviour.

**Suggestion**: Add a "SDK validation changes" section to the 1.9.0 changelog (and the PR description), audit the dependent plugins for the new limits (especially the batch size and price precision), and consider soft-warnings instead of hard errors where the API itself would still accept the payload.

### 3. [major] Connected view and status poll use `is_store_connected()` instead of `is_connected()`

**[file: omnisend/includes/Internal/class-connection.php | lines 153–155, 256]**

`show_connected_store_view()` and `send_connection_status()` only check the `store_connected` flag, while the PR itself introduces `Options::is_connected()` (flag **and** credentials) and `Omnisend::is_connected()` -> `has_credentials()`.

**Why**: After finding 1 (or any future token loss), the admin page shows the "connected" React view with only a "Go to Omnisend" button and no way to reconnect, while the SDK reports the plugin as not connected. Users end up in a state they cannot repair from the UI (the PR explicitly adds no disconnect action).

**Suggestion**: Use `Options::is_connected()` in both places so a credential-less store falls back to the landing page with the connect buttons; alternatively add a "Reconnect" action to the connected view.

### 4. [minor] OAuth client secret and refresh token are stored as autoloaded plain-text options

**[file: omnisend/includes/Internal/class-options.php | `set_oauth_tokens`, `set_oauth_client`]**

`update_option()` defaults to `autoload = yes`, so `client_secret`, `access_token` and `refresh_token` are loaded into `alloptions` on every front-end request and cached by object caches.

**Why**: Same exposure class as the existing API key, but the refresh token is long-lived and the client secret enables new token grants. Not autoloading them limits accidental exposure (e.g. plugins dumping `alloptions`, cache inspection) and avoids growing `alloptions` for anonymous requests that never need them.

**Suggestion**: `update_option( ..., $value, false )` for the five OAuth options (add the option first with `add_option( ..., '', '', 'no' )` where needed so autoload is respected on existing installs).

### 5. [minor] Raw upstream body leaks into admin notices

**[file: omnisend/includes/Internal/class-apiresponse.php | `status_error()` fallback (first 500 chars of body)]**
**[file: omnisend/includes/Internal/class-connection.php | lines 130–139]**

`get_connection_error_message()` appends `$error->get_error_message()` for transport, shape and default cases, and `ApiResponse` puts up to 500 characters of the raw upstream body into that message when there are no problem details.

**Why**: HTML error pages from a proxy/WAF or gateway diagnostics end up (escaped, so no XSS) in the admin notice. It is noisy and may reveal infrastructure details. Minor because the audience is `manage_options` users.

**Suggestion**: Cap the fallback to the HTTP status + reason phrase in admin-facing messages; keep the body snippet only in the `WP_Error` data for logging.

### 6. [minor] Single site-wide OAuth state transient

**[file: omnisend/includes/Internal/class-oauthclient.php | lines 47–49, `complete_authorization`]**

State is stored under one key `omni_send_core_oauth_state`. Two admins (or two tabs) starting the flow within the hour overwrite each other's state; the first one to return fails with a state mismatch, and — with finding 1 — currently also clears tokens.

**Suggestion**: Key the transient by state value (`set_transient( 'omni_send_core_oauth_state_' . $state, get_current_user_id(), HOUR_IN_SECONDS )`) and look it up by the returned state, or accept the limitation and make the mismatch path non-destructive.

### 7. [minor] Cached authorization in `Client` is never refreshed

**[file: omnisend/includes/Internal/V1/class-client.php | lines 719–735]**

`get_authorization()` memoises the Bearer header for the client instance's lifetime. For long-running processes (cron contact sync loops, WP-CLI imports) a token can expire mid-run and every following call gets a 401 without a refresh attempt.

**Suggestion**: Re-resolve the authorization on `ApiResponse::ERROR_UNAUTHORIZED` once (clear `$this->authorization` and retry), or resolve it per request — `OAuthClient::get_valid_access_token()` is cheap when the token is still valid.

### 8. [minor] Test gaps

- No test that an already OAuth-connected store survives a stray `error=`/mismatched-state callback (finding 1).
- No test for `Options::clear_oauth_tokens()` falling back to API-key mode when a legacy key exists.
- No test for `send_connection_status()` (nonce/capability/response).
- No test for the token *refresh* path in `ApiRequest::authorization()` failing (expired refresh token -> `ERROR_REFRESH`) through the SDK client.
- `connection-status.js` is untested (acceptable for vanilla admin JS, but note the `MAX_POLL_ATTEMPTS` = 10 min budget).

### 9. [nit] Style / consistency

- `class-oauthclient.php` token body: alignment `'client_secret'  => $client_secret,` has an extra space (PHPCS may flag `WordPress.Arrays.MultipleStatementAlignment`).
- `class-productvariant.php` `is_valid_price()` compares floats with `===` after `round()`; works for typical inputs but `abs( $a - $b ) < 1e-9` is more robust.
- `class-utils.php` `is_valid_identifier()` returns `int|false` from `preg_match` under a `bool` return type — fine due to coercion, but `=== 1` is clearer.
- `connection-status.js` opens the OAuth flow in a new tab and polls the current one; consider stopping polling on `visibilitychange`/unload to avoid 300 requests per idle tab.
- Bootstrap enqueues `connection-status.js` on the settings page even when the connected view is shown (no `.omnisend-connect-action` elements exist there) — harmless but avoidable.
- `readme.txt` changelog should mention the new `OMNISEND_CORE_API` / `OMNISEND_CORE_OAUTH_ISSUER` overrides for non-production environments, and the SDK validation changes (finding 2).

## Decision

**Request changes** (documented here only; no review was submitted on the PR at the requester's instruction).

Finding 1 is a correctness/security issue in the new credential lifecycle and should be fixed before release. Findings 2 and 3 are strongly recommended before 1.9.0 ships to wordpress.org because they affect dependent plugins and leave admins without a recovery path.

## Next steps

1. Make failed callbacks non-destructive for existing OAuth tokens and ignore `error=` without a pending state (finding 1); add regression tests.
2. Switch `show_connected_store_view()` / `send_connection_status()` to `Options::is_connected()` or add a reconnect action (finding 3).
3. Document SDK validation changes in the 1.9.0 changelog and check dependent plugins against the new limits (finding 2).
4. Store OAuth options with `autoload = no`, trim raw bodies out of admin notices, handle 401 by re-resolving the token in `Client` (findings 4, 5, 7).
5. Optionally key the state transient per attempt (finding 6) and address the nits.
